# 上下文压缩算法（用户可读版）

> 本文是 `02-agent-runtime.md` 与 `Forge.Core/SPEC.md` 压缩契约的用户向说明：同一个算法，写给要理解"模型看到多少、为什么被压、原文去哪了"的人。
> 公式与实现一致（`CompactionPolicy` / `AgentLoop` / `SummaryCompactor` / `ToolResultReduction`），代码改动时同步本文。

**一句话**：上下文用到**触发线**时，FORGE 先做**零成本的裁剪**（把最旧的工具输出换成一行收据），不够才把较旧的对话**压成结构化摘要**，并按一份预算表决定压到多小——原文一条不删，模型随时能查回来。

---

## 一、符号表（`*` = 用户可调）

| 符号 | 含义 | 单位 / 来源 |
|---|---|---|
| **W** | 模型的上下文窗口 | tokens；模型目录 / 提供商上报 / 「默认上下文窗口」设置 |
| **wireMax** | 请求真正带出去的输出上限（Anthropic 的 `max_tokens`） | tokens；Anthropic 取 `OutputCeiling.Wire`：模型钉值 ?? **8 192**，thinking 预算超过它时抬到"预算 + 4 096"；其它协议取模型的钉值（没有就没有） |
| **maxOut\*** | 模型的单条回复上限（能力值） | tokens；UI 两个入口：提供商编辑器「最大输出」、模型元数据窗口每模型列；空 = 未知 |
| **R** | 输出预留：给这一条回复留出的空间 | tokens，见 §3 步骤 0 |
| **U** | 可用输入预算：提示词能用的空间 | tokens，`U = W - R` |
| **trigger%\*** | 触发线 | 默认 85，范围 50–95 |
| **emergency%\*** | 回合内紧急线 | 默认 95，范围 90–99 且必须 > trigger |
| **target%\*** | 压缩目标 | 默认 50，范围 1 … < trigger |
| **keepRecent\*** | 原样保留的最新原文量 | tokens，可空（空 = 自动）；范围 1 000–1 000 000 |
| **τ** | 触发线的 token 数 | `τ = ⌊U × trigger%⌋` |
| **ε** | 紧急线的 token 数 | `ε = ⌊U × emergency%⌋` |
| **T** | 压缩目标的 token 数 | `T = max(1, ⌊U × target%⌋)` |
| **C** | 当前上下文（此刻模型要吃的 prompt 大小） | tokens，见 §3 步骤 1 |
| **Γ** | 迟滞用的"再生长量" | `Γ = ⌊0.1·U⌋` |
| **继承前缀** | fork / 交接继承来的父会话消息与摘要 | tokens，裁剪与压缩**都永不改动**（缓存契约） |
| **seq** | 每条消息在会话库里的自增序号 | 收据与摘要记录用它指回原文 |
| **收据（receipt）** | 替换掉一段旧工具输出的那一行文字 | 见 §4 |

---

## 二、三个前置概念

1. **窗口是输入与输出共用的一格**：`prompt + 回复 ≤ W`。所以先从 W 里划走 **R**，剩下的 **U** 才是提示词能用的。R 留少了，请求会被提供商以"太长"拒绝；留多了就等于白扔上下文。
2. **稳定前缀在请求里，但不在压缩的处置范围内**：系统提示、工具定义、渲染规则是固定缓存部分（system 字段 + 工具数组），裁剪与压缩都不碰它；换模型或改工具集才会让它失效。
3. **两级回收，先便宜后昂贵**：

   | 级别 | 手段 | 代价 | 什么时候用 |
   |---|---|---|---|
   | 第一级 | **裁剪**：旧工具输出 → 收据 | 0 模型 token，只重写一次消息前缀 | C 过线且还有窗口外的旧工具输出 |
   | 第二级 | **摘要**：把较旧对话压成结构化摘要 | 一次真实模型请求 + 前缀重写 | 裁剪不够（或已无可裁）时才用 |

## 三、算法步骤（精确版）

### 步骤 0 — 算 R、U 与三条线

```
R = wireMax                                          ← 请求真的会带这么多输出
    否则 min(maxOut, ⌊0.2·W⌋)                        ← 有模型钉值就取它，但封顶 20%
    否则 ⌊0.2·W⌋                                     ← 全未知时的保守代理
R = max(R, min(4096, ⌊W/2⌋))                         ← 保底：小窗口也要留得下一次像样回复
U = W - R
若 R ≥ W  → 这套机制整体不启用（窗口连自己的输出上限都装不下，压缩救不了）

τ = ⌊U × trigger%⌋        ε = ⌊U × emergency%⌋
T = max(1, ⌊U × target%⌋)  Γ = ⌊0.1·U⌋
```

**为什么优先用 wireMax**：Anthropic 的 thinking 预算与回答共用 `max_tokens`，请求实际带的输出额度可能比目录里的"能力值"更大。用能力值算 R 会让 R 偏小，`0.85·(W-R)` 就可能落在真实窗口之外——上下文早就爆了，压缩还没开始。

### 步骤 1 — 量 C（当前上下文）

- 模型没变、历史版本没变：`C = 上次请求的真实 InputTokens + 此后新增消息的折算`
- 否则：`C = 全部消息 + 稳定前缀 + 工具定义`（每个工具定义另加 8 token 包装）
- 折算：拉丁/代码每字符 2 单位、CJK/全角每字符 5 单位，8 单位 = 1 token（拉丁 4 字符/token、中文约 1.6 字符/token）；图片固定 1 600 token；附件 250 token/KB。

### 步骤 2 — 判该不该动

```
动手的条件 = 自动压缩开启
          且 压缩器不是空实现
          且 W 已知（R < W）
          且 C ≥ 当前这条线
```

**两条线怎么分工**（最容易误解的一点）：

| 时机 | 用哪条线 | 原因 |
|---|---|---|
| 回合的**第一个**请求前 | **τ（85%）** | 此刻上下文是上一回合留下的，动它不影响本回合证据 |
| 同一回合内的后续请求 | **ε（95%）** | 回合正在收集工具结果，压掉等于把证据烧了；只有快撞窗口才动手 |

`/compact` 手动压缩**不看任何线**，随时可用。

### 步骤 3 — 先试裁剪（第一级，零模型成本）

只在"该动手"之后才执行，**且不受 Stalled 与迟滞限制**（它也是唯一能把 Stalled 实例救回线下的手段）。

1. **不可裁的边界**：从最新消息往前累加，装入 `keepRecent` 的那一段窗口内一律不裁；`Inherited`（继承前缀）一条不碰。裁剪的收益上限因此是 `C - keepRecent`。
2. **候选**：窗口以外的 `ToolResultBlock`，满足"非错误结果"且（文本长度 > **512** 或含图片）。错误结果永远不裁（它是"要修什么"的锚点），≤512 字符的也不裁（省不下空间）。
3. **要释放多少**：`need = C - 中点`，其中 `中点 = T·(trigger% + target%) / 2`（默认 ≈0.675·U）。**与 C 同口径**（含稳定前缀与工具定义），否则小窗口下永远裁不到线下。
4. **按量贪心**：候选按"释放的 token 降序、等大取更旧"排，累加到 ≥ `need` 即停（用最少条数、最少收据）。
5. **替换**：把选中的结果块换成收据（块与 `CallId` 原样保留，providers 要求调用与结果配对）。
6. **记账**：`ReplaceHistory` 后重新量 C，发 `AgentContextReduced(before, after, 条数, read/bash/图片/其它 各自的释放量)` + `AgentContextMeasured`。
7. **判定**：裁后 **< 线** → 复位迟滞与 Stalled，本回合不再做摘要；仍 ≥ 线 → 带着新的基线进入第二级（**不复位**——否则继承前缀巨大的实例会逐轮绕过迟滞等待、每轮白烧一次摘要请求）。

**幂等靠一个定点**：任何渲染出来的收据都短于 512 字符，所以第二遍裁剪时它不再是候选；同一份历史重裁零变化，不需要"已裁过"标记。

### 步骤 4 — 算"原文尾能留多少"（第二级：摘要）

先算两个数，**它们是两个不同的量**：

```
rawBudget = T - 继承前缀 - 旧摘要          ← 可能为负（继承前缀很大时）
K         = 有效 keepRecent                 ← 见下
goal      = max(K, rawBudget)               ← 切点真正用的数
```

`K` 的夹取（顺序固定）：

```
K0 = keepRecent*（有值就用它） ?? min(20 000, ⌊0.2·U⌋)
K0 = clamp(K0, min(1 000, U), max(1, ⌊U/2⌋))     ← 设置值过大也压不到；U/2 是硬顶
K  = max(1, min(K0, ⌊T/2⌋))                      ← 自动/溢出路径再夹一次
```

### 步骤 5 — 选切点（从新到旧）

- 从**最新一条**往前逐条累加，累加量 ≤ `goal` 的**最长后缀**保留为原文；
- **切点只能落在 user 或 assistant 消息上**：不能是工具结果、不能是第 1 条；一条工具调用和它的结果**永不分开**；
- 一条都放不下 → 只保留"最新合法切点"之后的部分；
- 整条尾巴本来 ≤ `goal` → **不压**（本次什么也不做）。

### 步骤 6 — 生成摘要

- 输入 = `旧摘要（作为 previous-summary）` + 切点之前被切出的消息（按"一条 user/assistant + 其后的工具结果"为不可拆单元分批）；
- 摘要器看每个工具结果**最多 2 000 字符**、每个工具参数最多 500 字符；输出上限 8 192 token（拆分回合的前缀链 4 096）；
- 固定 6 段：**Goal / Constraints & Preferences / Progress（Done·In Progress·Blocked）/ Key Decisions / Next Steps / Critical Context**；逐字保留文件路径、函数名、错误信息；
- 摘要请求失败、被输出上限截断、或摘要器去调工具 → **整次压缩失败，一个字也不写**。

### 步骤 7 — 落库（一条记录，范围持续变大）

```
SummaryRecord( layer = 2,
               fromSeq = 上一份会话层摘要的 fromSeq（首次 = 该会话第一条被摘要的消息）,
               toSeq   = 切点前一条消息的 seq（#15 → 下次 #24 → …）,
               text    = 摘要正文 + <read-files> / <modified-files>,
               at      = 现在 )
```

- `summaries` 表**只 INSERT**，旧行不删、不更新；读取时取 `toSeq` 最大的那条；
- 原文（`messages` 表）**一条不动**，`fromSeq..toSeq` 只是"这段已被摘要代表"的逻辑标记。

### 步骤 8 — 重建上下文

```
新上下文 = 继承前缀（逐字节不变）
         + 一条 user 消息：摘要正文（含 "Session summary (messages #a-#b)" 抬头与文件清单）
         + seq > toSeq 的原文尾部
```

- 实际压后大小**可能低于 T**（消息粒度取整）；
- **可能高于 T**，但只可能因为「继承前缀 + 旧摘要 + K 地板」已经吃掉预算；
- 新的大小 `C'` 再判一次：`C' < 线` → 复位迟滞；仍超线 → 记一次"无效尝试"；**连续两次无效** → Stalled（`Ineffective`）；
- 重建后消息前缀变了，下一次请求会**重写提示词缓存**（系统提示与工具定义那部分仍命中）——这是摘要级的真实成本。

### 步骤 9 — 两种兜底与一个提前判死

| 情况 | 行为 |
|---|---|
| 提供商直接报"太长" | **不先裁剪**，直接强制压一次（目标 `min(C × target%, T)`），重发一次；再失败按原错误结束 |
| 手动 `/compact [关注点]` | `T = 1` → `goal = K`（只保留最新 K tokens 原文，其余全摘要）；关注点作为额外指令；不管开关与触发线；复位 Stalled |
| **不可压缩的下限** ≥ 线 | 摘要能做的最小体积 = 继承前缀 + 稳定前缀 + 工具定义 + `min(K, 现有)`（旧摘要按 0 算，因为它总还能被改写得更短）。一旦它已经 ≥ 线，**一次请求也不发**就判 `Irreducible`；之后只有两种情形会重新尝试：线抬高（换更大的窗口模型 / 调高触发比例）或工具集变小（工具定义变少） |

## 四、收据（receipt）长什么样

```
[omitted: read_history 118 · src/App.cs:1-420 · 32000 chars]
[omitted: read_history 119 · bash dotnet build src/Forge.App -c Release … · 480000 chars]
[omitted: image]
```

- **固定部分永不截断**：`read_history <seq>` 是找回原文的唯一入口；只缩路径（中间省略，保住根与文件名）或命令（尾部省略，保住动词与子命令）。路径/命令段上限 96 字符。
- 被裁的结果保留**头 150 + 尾 150 字符**（错误首行与结果行/退出码通常在这两端），中间换成上面那一行。
- 收据总长恒 < 512 字符 —— 这条不变量就是裁剪幂等的地基。

## 五、四个容易记错的地方

| # | 错误写法 | 正确的是 | 后果 |
|---|---|---|---|
| ① | `R = min(maxOut, 0.2·W)` | 先取请求真正带的 `wireMax`，否则 `min(maxOut, 0.2·W)`，否则 `0.2·W`；再抬到 `min(4096, ⌊W/2⌋)`；`R ≥ W` 时整体不启用 | 用能力值当预留会让触发线落在真实窗口之外；漏掉 4096 保底则 8k 窗口只留 1.6k，请求被测裁 |
| ② | 一个"目标预算"包办一切 | `rawBudget` 与 `goal` 是两个数：先减继承前缀与旧摘要，再对 K 取大 | `rawBudget` 可为负（fork 大父会话），直接当切点预算会得出"一条都留不下" |
| ③ | `keepRecent = 设置值 ?? min(20 000, 0.2·U)` | 还要夹 `[min(1 000, U), U/2]`，再夹 `⌊T/2⌋` | 不夹 `T/2` 时 keepRecent 可能比目标还大 → 永远压不到目标，每轮无效尝试直到 Stalled |
| ④ | 每次压缩写一条"对应本次切片"的记录 | 一条会话层记录：`fromSeq` **固定**、`toSeq` 每次前移，正文**增量更新**（旧摘要 + 新切出部分） | 照错误写法会以为每次要重读历史原文；实际第二次起只喂 `<previous-summary>` + 新消息 |

## 六、两个容易踩的实现细节

| # | 细节 | 具体后果 |
|---|---|---|
| ⑤ | 切点是**整条消息**，工具调用与结果不拆开 | 实际保留量常**低于** goal（一条消息跨边界就整条留下/整条压）；"压后大小"因此不精确等于 T |
| ⑥ | `<read-files>` / `<modified-files>` 由**代码生成**，不是摘要器写的 | 从被压区的工具调用抽取；`read` 记**实际显示的行范围**（截断时以回答里的 `Shown lines X–Y` 为准，不取请求的 limit）；跨压缩合并（相交或相邻即合并，`1-420` + `421-840` → `1-840`）；读过又改的只出现在 modified 下；渲染有字符硬预算（读 4 000 / 改 8 000，超出时补一行 `… N more`） |

## 七、两个完整例子（W = 170 k）

**A. Anthropic，模型未钉 maxOut**（`wireMax = 8 192`）：

```
R = 8 192            U = 161 808
τ = 137 536   ε = 153 717   T = 80 904   Γ = 16 180
K0 = min(20 000, 32 361) = 20 000 → K = min(20 000, 40 452) = 20 000
```

现在是回合的第一个请求，`C = 140 000 ≥ 137 536`，无继承前缀，旧摘要 3 000：

```
裁剪级：中点 = T(67.5%) = 109 220；need = 140 000 - 109 220 = 30 780
        窗口外有 4 条 8k 的旧 read → 裁 4 条（释放 ≈32 000）→ C ≈108 000 < 137 536 → 结束，不调摘要器
若没有可裁的旧输出：
rawBudget = 80 904 - 0 - 3 000 = 77 904
goal      = max(20 000, 77 904) = 77 904
从尾部累加：turn3 = 46 000 ≤ 77 904 ✓；再往前 turn2 → 80 000 ✗
→ 保留 turn3 原文，摘要 turn1-2
新上下文 = 前缀 12 000 + 摘要 2 000 + 原文尾 46 000 = 60 000（低于 T，因为切点在消息边界）
距下次触发还有 137 536 - 60 000 = 77 536
```

**B. OpenAI 兼容、无钉值**（`wireMax` 不存在）：`R = 0.2·W = 34 000`，`U = 136 000`，`τ = 115 600`，`T = 68 000` —— 也就是本文早期版本里那个例子。两种模型的差别只来自 **wireMax**：同一个 170k 窗口，Anthropic 因为默认只发 8 192 输出，能用的输入比"20% 代理"多出 25 808 token。

## 八、用户能看到什么、能调什么

| 你看到的 | 含义 |
|---|---|
| 输入框上条 `62k/170k · 36%` + 五段量规 | C / U · 占比；距触发线 10 个百分点变警告色、到线变超限色 |
| 量规旁 `Context 62k/170k (36%); auto-compaction at 145k.` | 同一读数也发给模型（设置里可关） |
| 会话内提示"已压缩 118k → 60k" | 一次摘要完成 |
| 用量读数里的"本次裁剪释放 …（read · bash · 图片）" | 第一级回收了多少、来自哪类工具。该读数已在 `SessionInstrumentsViewModel` 计算（`UsageReductionText` / `UsageReductionRatioText`），但**尚未绑定到任何面板**（见 `14-limitations.md`） |
| 提示"上下文仍高于触发线…已停止自动摘要" | Stalled（`Ineffective`）：连续两次摘要压不下来；`/compact`、换模型、或一次裁到线下都能复位 |
| 提示"无法再压缩…" | Stalled（`Irreducible`）：继承前缀 + 稳定前缀 + 工具定义 + 尾部本身已超线，一次请求都没发；换更大的窗口模型或调高触发线才可能恢复 |
| `search_history` / `read_history` / `read_artifact` | 模型（和你）找回**被压缩或被裁剪的原文**：消息表与 artifacts 从未删除 |

| 设置项 | 调大 / 调小的效果 | 建议 |
|---|---|---|
| 触发线 %（85） | 小 = 更早压、原文更早消失；大 = 压得更少但更容易撞窗口 | 80–90；中文或长文档会话 75 |
| 压缩目标 %（50） | 小 = 压得更狠、下一次更远；大 = 压得浅、更频繁 | 取触发线的约六成 |
| 保留最近 tokens（空 = 自动） | 大 = 原文留得多、压得浅（也意味着可裁的旧输出更少） | 1M 窗口的模型 100 000 |
| 回合内线 %（95） | 大 = 回合内几乎不压缩（证据更完整） | 保持 95 |
| 最大输出（空 = 未知） | 填准了 R 才准；填小了回复会真的被截断 | Claude 8 192，其它看模型 |
