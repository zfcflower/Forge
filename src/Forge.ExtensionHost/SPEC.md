# Forge.ExtensionHost

常驻 JIT 进程,主程序(Native AOT)的插件代理:发现、编译、审批把关、Worker 管理。主程序是它唯一的 IPC 客户端;协议见 `Forge.Plugin.Sdk/ExtensionProtocol.cs`。

## 边界

- 依赖 Ipc、Plugin.Sdk、Scripting、ScriptRuntime、Approval;不引用 Core、Abstractions。不加载插件代码:插件执行一律交给每插件一个的 `PluginWorker` 进程,脚本执行一律交给每次调用一个的 `Forge.ScriptExecutor` 进程(本进程只编译,不运行脚本)。
- 命令行:`--pipe`(必需)、`--plugins`、`--data`、`--dotnet`、`--worker`、`--executor`、`--tool-timeout`、`--concurrency`、`--script-workers`。Worker 定位:`--worker` → `FORGE_PLUGIN_WORKER` → 与 Host 同目录 → 开发布局兄弟目录;执行器定位同理:`--executor` → `FORGE_SCRIPT_EXECUTOR` → 与 Host 同目录 → 兄弟项目输出(进程内构造的 Host 留空时也按同一规则查找)。**显式给出的执行器路径不回落发现链**:`--executor` 或 `FORGE_SCRIPT_EXECUTOR` 指名了一个不存在/不是文件的路径时,调用以 `executor_missing` fail-closed 失败(消息带上该路径),不会退而启动另一个“碰巧找到”的执行器;只有完全没给出时才做目录/兄弟项目发现。`--dotnet` 只用于启动 `.dll` 形态的子进程(命令行=`<runtime> <dll> --pipe <name>`),不传给子进程——插件 Worker 只接受 `--pipe`/`--max-concurrency`,执行器只接受 `--pipe`。

## 关键决策

- **审批以磁盘字节为准。** `plugin.execute` 每次从磁盘重读并重算哈希,不信任缓存目录名;内容变更需 `plugins.refresh` 并重新审批。审批记录在 `<data>/approvals.db`(SQLite,WAL,见 `forge-approval`),损坏即 fail-closed 退出;Host 在 `DisposeAsync` 里关闭审批库连接(`ApprovalStore.Dispose`),因此 Host 退出后数据目录不残留 `-wal`/`-shm`、可整体删除。
- **审批绑定实际加载的字节。** 每个插件的“镜像”=入口程序集 + 其可加载目录(扁平依赖探测目录)`PluginImage` 内的**所有文件**,逐个按读到的字节算 SHA-256。`DependencyHash` 由 Host 自己的 `DependencyHashSchema`(schema 标记 `forge.dependency-fingerprint/v2`)算出:manifest 依赖、声明的权限与镜像内各文件摘要三类元组合入同一哈希,每条记录带 Host 生成的类别域(`dep`/`perm`/`file`),域、键、值三个字符串各自按 UTF-8 字节长度定帧;条目按序数排序,完全重复项折叠(权限的 scope 为空与缺省按登记期的同一规则视为同一项)。定帧与域是必须的:manifest 依赖名/版本是任意文本,旧的 `name@version` 加换行格式只在名字与版本都不含 `@` 和换行时才是单射,一个名为 `permission:<kind>` 的假依赖能与内部权限条目产生相同字节,于是“新增依赖”可以顶替“新增权限”而让旧批准继续有效;给内部条目加前缀只挡住那一个实例,挡不住换行/`@`/Unicode 造成的边界漂移。用户依赖数据永远落在 `dep` 域,不可能冒充内部权限或文件域。替换任一依赖 DLL、入口程序集或新增同目录文件都会使批准失效;哈希变更即 fail-closed,旧批准不迁移,需重新审批。`Forge.Approval.Hashing` 保持字节不变(其公开语义与既有测试继续有效),Host 只是不再用它的拼接格式承载依赖/权限/文件三类元组。加载前重新计算并作为 `worker.load` 的 `assemblySha256` 与 `files` 下发,由 Worker 校验并拒绝不匹配(换文件 → 拒载);Host 侧在发送前已按批准哈希比对,不匹配即 `plugin_not_approved` 且要求 refresh。`files` 的键是入口程序集所在目录下**递归**所有文件的相对路径(`/` 分隔),与 Worker 的“声明外文件一律拒载”规则同一范围;入口程序集自身也列入其中,digest 与 `assemblySha256` 同源(同一次读取)。
- **审批哈希经状态查询上报。** 发现时 upsert `Draft` 记录并刷新内容哈希,主程序通过 `plugins.status` 获取 sourceHash、dependencyHash、sdkVersion 与权限需求后调用 `plugin.approve`,不直接打开 Host 的审批数据库。批准在落盘前就在闸门内按磁盘当前字节重算并比对(`sourceHash`、`dependencyHash` 与 SDK 版本),不符即 `approval_mismatch` 且不写记录——陈旧批准不会写进审批库。若记录自身已标 `Approved` 却不再覆盖它所描述的内容(指纹对不上),该记录退回 `Draft`,以免留下“看似已批准、实际拒跑”的状态;仍持有可用批准时原样不动。`SetApproved` 之后 `ApplyCoreAsync` 会再次按磁盘重读内容:若此时内容或 manifest 已变,该次调用写入的 `Approved` 记录必须在抛出 `approval_mismatch` 之前退回 `Draft`,不能留下“刚批准、已不覆盖磁盘”的记录。退回是**闸门内 + 哈希条件**的:只有记录仍是 `Approved` 且 source/dependency/SDK 三个哈希仍等于本请求写入的值时才退回;记录已被另一写入方(含外部进程)改成更新的哈希或非 `Approved` 状态时不动,不撤销别人的新决定。
- **审批变更与执行串行。** 每插件一把异步闸门(生命周期跨 WorkerSlot):`plugin.approve`/`plugin.revoke`/`plugins.refresh` 与一次执行的“重算哈希→审批校验→确保 Worker 已加载→再校验→派发”互斥。执行在离开临界区前登记在途计数;`plugin.revoke` 在闸门内作废批准、注销工具、杀 Worker 进程树(以此终止在途调用)、等在途计数归零后才返回,因此 revoke 之后不会再有新执行启动、也不会有被恢复的 Worker 残留。
- **闸门按根归属,不按插件名。** 闸门的持有者记录为**根调用令牌**(`rootRunId`):顶层执行、`plugin.approve`/`plugin.revoke`/`plugins.refresh` 以“独占”身份排队等闸门;嵌套调用只在两种情形下进入临界区——闸门空闲,或闸门正被**同一个根**的执行持有(此时按持有计数再加一层,兄弟子调用并行做哈希/装载/发布),否则立即 `plugin_busy`。闸门由最后一个持有者释放时才交给队列里的下一个独占等待者,所以嵌套调用永不排在另一个根后面,也不会被“先看再等”骗过去;准入判定与持有更新在同一把锁内完成,不存在“检查时同根、等待时换人”的窗口。一旦有独占调用在排队,新的同根嵌套调用就改为 `plugin_busy`,避免持续重入饿死审批/刷新。跨根拒绝的最终判定仍在在途表(见下条),闸门这一层只是让同根兄弟不再互相误判。
- **条目生命周期:闸门内换、闸门内判。** 每插件状态 `PluginState`(连同它的闸门)以插件 id 为键、贯穿整个 Host 生命周期,`plugins.refresh` **永不丢弃**它(包括插件已被删除时)。`plugins.refresh` 在**刷新级闸门**内逐个插件再取该插件的闸门,并在该闸门内完成:用扫描结果替换 `plugins[id]`、`SyncRecord` 同步审批记录、插件缺失时注销工具并停 Worker。`plugin.execute`/`plugin.approve`/`plugin.revoke` 允许先在闸门外捕获条目,**拿到闸门后必须按 id 重新解析**当前条目:插件已删除 → `unknown_plugin`;条目已被替换 → `plugin_changed`(每次 `plugins.refresh` 都为发现的插件重建条目对象,所以闸门前捕获的条目一律失效,调用方重试即可);绝不使用闸门前的旧条目继续哈希校验、装载或派发。锁序固定为**刷新级闸门 → 每插件闸门**,任何路径都不按相反顺序获取,因此不会死锁。
- **测试钩子仅存在于 Debug 构建。** Host 内有一个内部 seam `IHostTestHook.AfterEntryCapturedAsync`(位置:`plugin.execute` 捕获条目之后、取该插件闸门之前),仅当环境变量 `FORGE_HOST_TEST_HOOK` 指向的 JSON 文件(`{"pipe":…,"directory":…}`)pipe 名与本 Host 相符、且目录内存在 `armed` 标记时启用;集成测试用它把一次执行卡在“已捕获、未取闸门”的窗口里,再改动插件目录并 `plugins.refresh`。钩子等待有上限,不会永久卡住 Host。`#if DEBUG` 编译:Release 构建里既没有 `IHostTestHook`/`FileHostTestHook`,也不会读该环境变量——生产 Host 即使继承到这类变量依旧照常执行。依赖钩子的集成测试先按 `Forge.ExtensionHost.dll` 的 `AssemblyConfigurationAttribute` 确认被测 Host 是 Debug 构建,否则以 `integration tests require a Debug build of Forge.ExtensionHost` 失败,不做静默跳过。
- **Worker 生命周期。** 超时、崩溃、取消后不合作的调用、启动/加载失败一律计一次异常事件(见失败预算),杀进程树、重启、重载、必要时重新注册工具,只失败在途调用。`host.tool_call` 经 Worker 管道到 Host 再中继主程序,Worker 不自开主管道;Worker 只发 `{runId,name,args}`,Host 按本会话 active-run 表补上 `pluginId` 后转发(见下),Worker 自报的 session/directory/depth 不读。`worker.execute` 携带 Host 校验过的 `context` 与 `timeoutMilliseconds`。
- **失败预算。** 每插件一个连续失败计数(在 `PluginState`,与 WorkerSlot 解耦、跨 slot 重建存活):4 次异常事件后拒绝一切执行(`worker_disabled`),只由 `plugins.refresh` 或一次真正完成的成功工具调用/命令/提示词求值清零。启动成功、加载成功、`plugin.approve` 都不清零。`plugins.refresh` 清零时若该 Worker 已因预算耗尽停摆,先丢弃 slot 与已发布的工具登记,重载成功后重新 `tools.register`(声明没变也重发),所以刷新后 Worker 重新运行且工具重新可见。
- **取消。** 调用方取消后不立即杀进程:Host 再等一个可配置的宽限窗口(`WorkerSlot.CancelGraceWindow`,默认 2 s)让该执行自行完成;窗口内完成则按正常结果返回,否则取消该请求(尽力发出 IPC `cancel`)并杀 Worker 进程树、重启并重载,计一次“取消杀”。工具超时监督独立于调用方取消:请求本身带 `--tool-timeout` 期限,超时照旧杀进程树。IPC 层把“下发 cancel”与“放弃本地响应”绑在一起,所以宽限窗口内 Host 只能等 Worker 自行完成,无法既下发 cancel 又观察结果;插件若只在收到取消后才退出,会走到杀进程树那一支。
- **进程树所有权(Windows:Job Object;Linux/macOS:进程组)。** 每 Worker 一个私有 Job Object:`CreateJobObject` → `SetInformationJobObject(JobObjectExtendedLimitInformation)` 只置 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`,不置 `BREAKAWAY_OK`/`SILENT_BREAKAWAY_OK`。进程启动后**先** `AssignProcessToJobObject` 再发 `worker.load`;选定的握手就是“Host 在分配完成后才发 `worker.load`”(Worker 连上管道后一直空闲直到收到 `worker.load`,因此插件代码不可能在分配前运行),子进程自动继承 Job,Worker 自身不需要做任何事。需要 Windows 8 / Server 2012 以上(嵌套 Job);Win7 上若 Host 已在某个 Job 内则分配失败,按下面的 fail-closed 处理。Host 存活期间,Worker 退出/崩溃/被杀/超时/取消/撤销/卸载一律 `TerminateJobObject` 再关句柄,所以**即便 Worker 已自行退出(崩溃),它留下的后代也会被杀**;Host 退出或崩溃时由操作系统按 KILL_ON_JOB_CLOSE 清空每个 Job。
- **失败即封闭(fail-closed)。** Job 创建、限额设置、分配任一失败:杀掉刚启动的 Worker 并报 `worker_start_failed`,**绝不在 Job 之外运行插件代码**。POSIX 上同一道关卡在 `Assign(int)`:`getpgid(pid) != pid`(组不是它自己的)一律报 `worker_start_failed`,因为此时 `kill(-pgid)` 要么得 `ESRCH`、要么在 pid 被复用后误杀别的组,两者都不能算“已归属”。集成测试用环境变量 `FORGE_HOST_TEST_FAIL_JOB_ASSIGN=1` 强制分配失败来覆盖该路径;该变量只由 `WorkerProcessOwnership` 在 `#if DEBUG` 里读取,Release 构建不含这段代码、也不读该变量,因此生产环境里 Worker 照常启动;两个 `Assign` 重载共用这一个钩子,所以该路径在 POSIX 上同样被覆盖。
- **Linux/macOS 的归属:Host 侧 `posix_spawn` + `POSIX_SPAWN_SETPGROUP`。** 组不再由 Worker 自己建立(`WorkerProcessGroup` 已删,Worker 不含任何 P/Invoke)。Host 在 POSIX 上用 `posix_spawnp` 起 Worker 与执行器:`posix_spawnattr_setpgroup(0)` + `setflags(POSIX_SPAWN_SETPGROUP)` 让子进程在第一条指令执行前就是自成一组的组长;stdout/stderr 经 `pipe2(O_CLOEXEC)`(Linux)或 `pipe` + `fcntl(FD_CLOEXEC)`(macOS,无 `pipe2`)重定向,由 `adddup2`/`addclose` 文件动作在 spawn 阶段完成;stdin、工作目录与环境照旧继承。`argv`/`envp` 在 `posix_spawn` 返回后立即释放(它返回时子进程已 exec 或已失败),环境内容是 `Environment.GetEnvironmentVariables()` 的托管快照(Host 内没有库直接 `setenv`,否则该变量会被漏掉)。`Assign(int)` 只记录 pid、用 `getpgid(pid) == pid` 校验并启动收割循环。**收割是必须的**:BCL 不收割非自己启动的子进程,不收割的时候子进程永久为僵尸,`Process.HasExited`(对非子进程用 `kill(pid, 0)` 判定)便永远为假,所有“进程树是否真的消失”的验证都会失效。收割顺序为 `waitid(P_PID, pid, …, WEXITED|WNOHANG|WNOWAIT)` 观察退出 → `kill(-pgid, SIGKILL)` 趁 pid 未被释放(僵尸仍持有 pid,组号不可能被别的进程占用)扫掉残留组员 → `waitpid` 释放 pid;只做到 `waitpid` 会把 pid 复用窗口从“僵尸持有期间”放大到“子进程退出 → 槽位处置”。组一旦这样关闭就不再发第二次组信号(`Kill` 直接返回上一次的扫组结果),以免释放后的组号归别人时误杀。每个 POSIX 子进程一条 1 ms→100 ms 退避的轮询任务(不占线程,只有 timer),Windows 侧没有。macOS 的 Unix 域套接字完整路径上限为 104 字节,`WorkerProcess.BuildPipeName` 因此按 `IpcPipe.MaxNameLength`(见 `forge-ipc`)给名称留出预算:唯一段与固定前后缀先占位,剩下的额度才给插件 token,长插件 id 不会生成超限管道名。Linux 已在 WSL2 上实测(0 warning/0 error,`ProcessOwnershipTests` 6/6,现有集成测试全绿;终端的 POSIX PTY 分支也在同一环境用一次性的真 Host 探针跑过 `/bin/sh`:主从端、`TIOCSWINSZ` 初值与 resize、SETSID 后的会话/组归属(pid=pgid=session)、0/1/2 指向同一从端且为控制终端、回显与输出、正常退出码与 128+信号、`tcgetpgrp(master)` 前台检测两个方向、`terminal.stop`/`host.stop`/主管道断开后整棵会话消失且 Host 退出码 0、stderr 无清理告警;`StopLifecycleTests` 在 Unix 上读非子进程 `ExitCode` 的缺陷已通过 `ExtensionHostClient.HostExitCode` 修复),**macOS 完全未验证**:`pipe`+`fcntl`、`WNOWAIT` 常量(`0x20` 而非 Linux 的 `0x0100_0000`)、`siginfo_t.si_pid` 偏移(`12` 而非 glibc 的 `16`)都只在代码里按 `OperatingSystem.IsMacOS()` 分岔并标注待 CI 验证,不得据此声称 macOS 已支持。
- **POSIX 进程组不是硬边界。** 后代自己调用 `setsid`/`setpgid` 即可脱离,要不可逃逸需要 cgroups(不做);POSIX 没有 KILL_ON_JOB_CLOSE 的等价物,Host 被强杀时 Worker 只会在管道断开后自行退出,其残留后代不被清理——不得宣称与 Windows Job Object 等价。
- **P/Invoke 隔离。** 约束见 `forge-architecture`:原生进程归属调用只允许在 Host 一个内部类内。现已满足:唯一的原生类是 `WorkerProcessOwnership`(Job Object、进程组、spawn、收割全在这一个类),`Forge.PluginWorker`(原先的 `WorkerProcessGroup` 已删)、`Forge.ScriptExecutor`、`Forge.ScriptRuntime` 与 Native AOT 主程序均无 `DllImport`/`LibraryImport`,也无 unsafe。
- **进程树清理顺序。** 停止 Worker 时:尽力发 `worker.stop` 并给 `StopGraceWindow`(2 s)让它自行退出 → 按上面的 Job/进程组杀树(该步骤不依赖 Worker 仍存活)→ 兜底 `Process.Kill(entireProcessTree: true)` → 再拆管道/对端并关闭 Job 句柄。POSIX 上第一步之后的 `kill(-pgid)` 在槽位处置早于收割时是必须的(子进程已退出但未被收割,组号仍属它);若收割循环已经扫组并释放了 pid,`Kill` 不再发组信号。超时、取消、撤销、崩溃恢复走同一条清理路径,失败预算/重启/取消逻辑不变。
- **产物布局。** 编译产物按缓存键内容寻址存放,未改动的插件不重编(命中后仍逐个重算镜像文件摘要);无源码的预编译插件按程序集字节哈希。
- **坏插件不拖垮启动。** 每个插件的发现/准备(`manifest.json` 解析、源码读取、编译、镜像哈希)都包在 try/catch 里:文件/路径/无效包错误一律转成 `PluginIssue`(取消异常照抛),健康插件照常注册。manifest 的 `id`/`version` 按 `VersionedOutputStore` 的路径段规则校验(拒绝 `..`、非法文件名字符、首尾空白、路径分隔符),读取器接受的值不会在后面拼路径时才抛异常。
- **调用绑定:回调只认 runId。** 主程序为每次执行分配 `ExtensionCallContext`(`runId/sessionId/workingDirectory/depth/pluginChain`),新请求必定携带;Host 校验其形状:runId 仅 `[A-Za-z0-9_-]` 且不超过 128 字符、工作目录必须是完全限定的绝对路径、depth 在 0–8、链不超过 8 环且无重复/空白、目标不在自己的链里(否则 `chain_cycle`)、有链时 depth 必须 ≥1。旧式只有顶层字段的 `plugin.execute` 作为可信根调用兼容路径保留,由 Host 用随机 runId 现场构造 context;`code.execute`/`plugin.command`/`plugin.prompt` 缺 context 一律 `invalid_context`。context 另带 `rootRunId`:顶层等于 `runId`,嵌套调用由主程序从可信父调用继承,Host 只校验形状(`[A-Za-z0-9_-]`,≤128 字符)不推算;空链且缺 `rootRunId` 的旧调用按“根即本 runId”补全,链非空却缺 `rootRunId` 一律 `invalid_context`——拿插件身份或链首项当根正是把独立脚本混成同一个根的原因。Worker 回调只带 `runId`,不能提供或替换根。派发前 Host 在该 Worker 会话的 active-run 表登记 `runId → (插件身份, 原始不可变 context, 根调用令牌, 生命周期)`;Worker 回调命中本会话表且仍在途才被补上 `pluginId` 转发主程序。未登记、已结束、迟到或跨 Worker 的回调在转发前拒绝(`unbound_tool_call`),不进入主程序解析器。执行结束(正常、取消、超时、杀进程)立即注销并取消该 run 的生命周期,所以插件忽略取消令牌也留不下可用的绑定。
- **run_code 身份与嵌套。** `$run_code` 是脚本保留身份:插件不得以它注册或执行(`reserved_identity`);`code.execute` 只允许空链(脚本或插件里不能再调 `run_code`,`run_code_nested`)。链与深度由主程序提供,Host 只校验不推算。
- **嵌套目标已忙即拒,同根兄弟排队。** 每插件状态记录在途执行按 `rootRunId` 调用令牌的分布(不用插件名、也不用 `$run_code` 代替);嵌套调用(链非空)遇到目标已有**另一个根**的在途执行、或目标插件闸门正被另一个根、审批、刷新或排队的独占调用占用时立即 `plugin_busy`,不排队等闸门,因此 A→B 与 B→A 两条根链不可能互相等待。跨根判定只在确认是不同根之后做;同一根下的兄弟子调用(含并发上限已满时)照常排队等 Worker 槽位,不因槽位满而被拒——否则一次脚本的并行子调用会被误判为交叉等锁。**同根不同分支的等待环:** 闸门本身放过“同根但不同分支”的互等,因此 Host 另有一份根内 wait-for 图,只记录**真正排队**的插件执行槽等待(立即拿到槽位的调用不登记):边的来源插件取可信调用链的最后一项(链为空或 `$run_code` 表示不是插件持有执行槽,不登记),目标是该槽的插件,边属于实际的 `rootRunId`。检查与登记在同一把图锁内原子完成,不持有其它锁、不 await;若新边会闭合成环(自环、`P→Q` 对已有 `Q→P`、更长的 `Q→…→P`),立即拒绝这一条边并报 `plugin_wait_cycle`,另一条边照常排队。相同边按引用计数合并,因此同一分支对同一目标的普通扇出仍然排队、不会被拒。边在取得槽位、取消、deadline、错误、revoke、slot 处置与关闭时释放,不留“假忙”的陈旧边。策略是保守的潜在环拒绝(可能拒掉本可等到释放的复杂调用),不声称对多资源实例做精确死锁检测。`plugin.execute`/`plugin.command`/`plugin.prompt` 三条执行路径共用同一套准入规则、同一份在途表与同一份等待图。
- **每请求预算,不是每连接默认值。** Worker 管道与主管道的 `IpcPeer` 默认超时都设为无限,避免旧的 120 s 默认截断合法脚本;每次调用自带 deadline:插件工具取请求 `timeoutMilliseconds` 并以 `--tool-timeout` 为上界,命令/提示词取请求预算并夹到 1–600000 ms,脚本取请求预算并夹到 1–600000 ms;`worker.load`/`worker.unload` 仍以 `--tool-timeout` 为界,`worker.stop` 仍用 2 s 常量。`host.tool_call` 中继不设连接级期限,由该 run 的生命周期(随本次执行结束)与主程序自身预算收口。**插件工具/命令/提示词共用一条在请求入口算出的绝对 deadline**,至少覆盖“等闸门/重算哈希/确保已装载 + 排队等执行槽 + 派发”,并且链接父调用取消、Host 关闭栅栏与该 slot 的生命周期;排到槽位后派发只拿**剩余**预算(Worker 收到的 `timeoutMilliseconds` 也是剩余值),等待之后不重置计时器。预算在**派发前**用尽时返回 `plugin_queue_timeout`:不杀本次调用尚未执行过的健康 Worker、不计失败预算;真正派发后超期才按既有语义杀整棵进程树并计一次异常事件。调用方取消仍走宽限窗口,与 deadline 到期区分。同根潜在等待环因此不会被拖到默认 60/120 s 才失败。
- **一次性执行器取代脚本 Worker 池。** `code.execute` 在每次调用时编译一次(Host 持有唯一的 `ScriptCodeCompiler`,缓存键=`编译表面指纹+源码+全部选项`)并 spawn 一个**全新**的 `Forge.ScriptExecutor`:Windows 下与插件 Worker 同一套归属(每执行器一个私有 Job Object + `KILL_ON_JOB_CLOSE`),POSIX 下也是同一条路径(`posix_spawn` 让执行器同样自成一组的组长,`kill(-pgid)` 恒有效),产物经 `executor.load`(base64+描述,单帧 < 16 MiB)在内存交付,`executor.run` 只拿**剩余**预算。结果、取消、超时、崩溃、`RequiresTermination` 之后,Host **先杀掉并等待整棵进程树**才返回该调用;杀不掉/等不到就把该问题**追加到结果文本**(不论结果原本是不是错误)、写入清理报告,并且绝不把这次调用说成成功。已执行过的进程绝不复用,也不以线程/静态状态/句柄污染检测决定是否复用。`--script-workers`(默认 4)现在只是**并发槽位上限**,不是池:每个槽一次只服务一个执行器进程。deadline 覆盖排队+编译+启动+装载+运行,总期限与杀进程树归 Host。**运行的等待同时挂在绝对 deadline 与调用方令牌上**:执行器对端没有默认超时,若只等调用方令牌,一个把线程池饿死/暂停自己的脚本就会让槽位与调用方一起无限等下去;因此 deadline 到期时 Host 立即取消该次等待、立刻 `CancelAsync`+`DrainAsync` 并抛出取消,由既有的“未在预算内完成、整棵进程树已被杀”结果路径收口(该路径因此不再不可达);调用方取消仍先给 2 s 宽限窗口,两者保持可区分;**宽限窗口内的等待同样挂在 deadline 上**:只有调用方取消时才能得到完整窗口,deadline 在宽限期内到期就立即停止等待并杀树,硬预算不会被宽限吃掉(不再有最多 2 s 的越界),取消报错文本也据此区分“宽限窗口内未停止”与“预算先结束”。**执行器登记随调用结束而清空**:`live` 表在 finally 里 `DisposeAsync` 之后于同一把注册锁内移除该次执行,注册表不会按调用次数增长,关闭时也不会再遍历到已结束的历史。同一次执行的问题只记录**一次**清理报告:记录在 `ScriptExecution.DisposeAsync` 的单飞完成里(两条处置路径共用的那一处),关闭路径不再重复记录同一个问题;调用方仍照旧在结果文本里看到它。`executor.load` 被执行器拒绝(error 应答)映射为 `executor_load_failed`,`executor.run` 被拒绝映射为带原因的失败 `CodeExecutionResult`(不再落成未分类的 `handler_error`);`IpcRemoteException`/`ScriptArtifactException` 都有明确归宿。
- **执行器启动与关闭的登记。** 启动尝试的计数与“是否已处置”在同一把注册锁内判定,进程从操作系统创建的那一刻起就登记到待处置集合,并链接关闭栅栏令牌;因此关闭时不会漏掉一个已经存在但还没发布的执行器,也不会在处置快照之后才 spawn。栅栏升起后新调用得到 `host_stopping`,启动中的执行器由启动方在锁外销毁,残留进程由关闭路径先杀后拆。预算在启动过程中到期时返回预算耗尽的 `CodeExecutionResult`,真正的调用方取消照常传播(宽限窗口后杀树并抛 `OperationCanceledException`)。**预算在 `executor.load` 阶段(尚未派发 `executor.run`)到期时措辞必须区分**:文本说明预算在镜像装载期间就结束、运行从未派发,而不是声称脚本“未在期限内完成”;同样在 finally 里杀整棵进程树并返回错误结果。取消一个脚本不影响其他脚本。
- **非 UI 贡献快照。** `worker.load` 的 `tools` 之外增加完整 `PluginContributionSet`;Host 在启动、approve、refresh、恢复时同时发 `tools.register` 与 `contributions.register`(整体替换,内容不变才去重),撤销、移除或刷新失败时同时发 `tools.unregister`/`contributions.unregister`,主程序因此不会留下过期贡献。**发布去重以“整帧已写入并 flush 完成”为准:** 每插件一个发布串行位与一份“主程序已知快照”记录,载荷只在 `SendNotificationAsync` 返回成功(transport 写完并 flush)后才写入去重表,因此在装载之后被取消或发送失败的发布不会被记成“已发布”——下一次装载/刷新/执行会重发,元数据不会永久丢失。这里只是**传输完成**,不是主程序的确认:IPC 没有应用层 ack,Host 从不知道主程序是否处理了某一帧,注释与实现都不得把它写成“已送达/已确认”。注册路径保持“发送成功后才记录”。注销路径保留**待注销墓碑**:记录的载荷只有在对应 `unregister` 帧写完并 flush 之后才清除,transient 写失败不会让后续注销被永久抑制(下一次 revoke/移除/reset 会重试);注销先把已知代号推进到当前装载代号,因此注销之前算出的旧发布不会把已撤销的插件重新登记回去。整帧写入被取消或失败时连接可能已写下半个帧、帧边界不再可信:Host 把连接标记为不可用并通过既有的受监督关闭路径退役(只置标志并结束 `RunAsync` 的等待,由 `RunAsync` 统一拆管道与 Worker),绝不在自己的请求处理器里 await 该 peer 的停止,也不再发送任何帧。发送自带期限(不挂在调用方令牌上、也不无限等待),Host 正在停止时不再发送。崩溃恢复后的重发会先确认插件仍在发现表中且仍被允许运行,迟到的恢复不会把已撤销的工具装回去。命令与提示词分别走 `plugin.command`/`plugin.prompt`(SDK `CommandExecutionRequest`/`PromptExecutionRequest`),与工具一样先重算镜像哈希、重新审批,只在批准后装载并派发;超时/崩溃走同一异常事件与失败预算。元数据(Markdown 工作流、Agent、面板声明、权限)只传输,不在 Host 执行,工作流不进入 `Forge.Workflows` JSON 执行。
- **plugins.status 不执行插件代码。** 返回每个已发现插件的 `PluginStatusInfo`:id/version、状态(`draft`/`approved`/`disabled`/`uninstalled`,无内容为 `invalid`)、发现时的 sourceHash/dependencyHash/sdkVersion、manifest 权限与发现/装载错误。审批记录每次从 SQLite 存储重读(`ApprovalStore.Get` 按 `data_version` 刷新),外部撤销立即可见;整个查询不装载插件、不调用 `Register`。manifest 在发现之后被改过时,状态查询不能给出“approved 且无错误”:这种情况返回错误诊断(内容已失效、需 refresh),说明上报的哈希是发现快照而非磁盘现状。判断只重读 `manifest.json`(与批准闸门同一个廉价检查),不执行插件代码、不重新计算或捏造当前内容哈希;记录本身不动,refresh 后才重新取哈希并由用户显式重新批准。状态字符串仍只用上述已知 wire 值,不引入新状态,也不因诊断自动批准。
- **manifest 权限进入审批哈希。** `manifest.json` 新增 `permissions:[{kind, scope?}]`(kind 为 `PermissionKind` 名称或 0–4 序号;未知值、空 scope、重复项都是 manifest 错误);在批准前读取并随状态上报,不靠执行插件发现。权限以 `perm` 域条目(权限种类名 + 规范化 scope)折进 `DependencyHash`,追加或修改权限即让旧批准失效,不需要依赖 SDK 版本号变化。依赖条目同样经长度定帧,manifest 依赖只要求名字非空、版本可为空字符串(表示不锁定),名字与版本可以是任意文本而不必靠拒绝 `@`/换行/Unicode 来掩盖编码碰撞。运行时 `RequirePermission` 必须是 manifest 权限的子集,否则 `worker.load` 以 `load_failed` 拒绝。`manifest.json` 不在可加载镜像内,所以执行与批准前都会重读:`permissions`、`dependencies`(按规范化的 (名字, 版本) 元组排序比较,与哈希的无序语义一致)与 `entryAssembly` 任一与发现快照不一致时,批准与 `plugin.execute`/`plugin.command`/`plugin.prompt` 一律按“内容已变、需 refresh”拒绝(fail-closed)。**新增依赖而不 refresh 也必须失效**,即便这次执行还不会加载那个依赖:依赖哈希只覆盖 Host 已经知道的声明,否则改 manifest 加一条依赖就能让旧批准继续有效。manifest 读不出来同样按已变处理。
- **旧 plugin.json 只报诊断。** 插件根下只有 `plugin.json` 的 1.x 包产生 `LegacyPluginPackage` 问题(stderr),不解析、不装载、不执行 `IForgePlugin`,也不做兼容适配。
- **关闭栅栏。** `host.stop`、连接关闭或 `DisposeAsync` 都先把“正在停止”置为不可逆,然后才快照、关闭主管道、拆资源;此后**新到达**的 `plugins.*`/`code.execute` 一律 `host_stopping`(`host.stop` 本身仍可应答)。`host.stop` 收到即升栅栏(不等回答写完),因此启动刷新里正在进行的装载/启动会被立刻取消,而不会让 Host 卡着 connect/load 窗口。**关闭单飞:** 栅栏与唯一的收尾任务在同一把注册锁内建立,`RunAsync` 的收尾、`DisposeAsync` 以及任何其它停止路径都 await 同一个任务,后到者不会因为“已处置”标志提前返回;`DisposeAsync` 还等到主管道真正关闭(有界)与审批库释放之后才返回,所以调用方拿到返回时 Host 已不再应答、也没有收尾还在进行。脚本监督器与每个 slot 的 `DisposeAsync` 同样是单飞:并发处置等待同一个完成,而不是后到的那个直接返回。所有可能新建 Worker 的路径在各自的闸门或注册锁内复查栅栏:`GetWorker` 在 Host 注册锁内判定(不会在关闭快照之后重建 slot)、`EnsureLoadedAsync` 与 `RecoverAsync` 在插件槽闸门内判定(恢复路径用 `CancellationToken.None`,所以必须靠栅栏而不是取消来阻止重启)、脚本监督器在槽注册锁内判定。启动中的 Worker 从**操作系统真正创建进程的那一刻**起就登记为“在启动”(先把该进程加入待处置集合,再继续归属分配与连接),并链接到栅栏令牌以便立即中止:关闭时先按有界窗口等这些启动尝试收尾(收尾指进程已被杀并拆干净,不是连接已被取消),再对仍然存在的进程先杀后拆;正在启动的 Worker 若发现栅栏已升起,由启动方在锁外销毁,绝不回池、绝不交给调用方。被 revoke、refresh 或装载失败移出注册表的 slot 以“退役任务”登记,关闭时一并按有界窗口等待,因此并发关闭不会漏掉一个已经不在快照里、却仍在杀进程的 slot。清理结果必须**可验证**:Kill / `TerminateJobObject` / `kill(-pgid)` 的返回值、`Process.Kill` 的异常与 `WaitForExit` 的结果都不得吞掉;判定“进程已消失”以观测到的进程状态为准,Windows Job 只是首选手段,不是唯一证据。`Process.Kill` 抛错、等待超时、进程仍存活、slot 退役窗口(30 s)用尽、主管道在关闭窗口内未关闭,都写 stderr 诊断并记入 Host 的清理报告。`RunAsync` 在清理报告非空时返回非零退出码,`DisposeAsync` 在同样情况下抛出 `host_shutdown_failed`,不静默成功;被 revoke/refresh 提前触发的清理失败同样计入,直到 Host 结束。正常关闭仍然退出码 0。因此 `DisposeAsync` 返回后(或抛出时)没有**可验证的**残留 Worker 进程,也不再有新 Worker 被接受;无法验证时如实报告,不声称“无残留”。快照先于杀进程,杀进程先于关闭主管道;任何等待都在锁外进行,不在持锁期间 await,也不在自己的收尾里递归调用收尾。被关闭打断的在途调用**不作回答**:连接关闭本身就是回答,调用方看到的是连接结束,而不是一个“Host 已经不在了却仍然给出结果”的帧;栅栏升起之后才到达的请求仍照常收到 `host_stopping`。
- 工作流引擎(Forge.Workflows)已引用但尚未接线。无向主程序推送插件问题的协议操作,问题仅写 stderr。

## 验证约定

同根扇出须核对完整结果数量与每项结果,不能反复检查同一个成功片段。跨根交叉调用以进入与完成两道因果门闩维持两个外层租约,不能靠自然调度假定双方同时占用。真实短预算成功用例只隔离本测试程序集内的并行编译负载,不扩大预算、不重试,也不承诺任意跨进程负载下都能在同一期限内完成。同根饱和的 P/Q 互等须在真实 Host/Worker 链路上验证其中一条快速以 `plugin_wait_cycle` 结束而不是等满默认预算;简单扇出到同一目标仍须全部排队成功;排队期间短 deadline 到期须返回 `plugin_queue_timeout`,持有者继续完成、其 Worker 不因该请求被杀、失败预算不增加;关闭清理失败须体现为非零退出码或 `DisposeAsync` 抛错,而不是成功。

## 已知缺陷与待验证设计

同根不同分支可能分别持有 P/Q 插件槽位并等待对方,单条调用链无环仍不足以保证资源有进展。已实现的契约(见“关键决策”的根内 wait-for 图与每请求预算):普通兄弟在同一总预算内排队,实际的执行槽等待形成潜在环时快速拒绝一条分支并给出原因(`plugin_wait_cycle`,允许保守拒绝),不扩大并发也不杀其他持槽调用;排队超时(`plugin_queue_timeout`)不杀该请求尚未派发的 Worker。根令牌与单链防环本身不足以解决它。

脚本的跨调用隔离由“一次性执行器”从构造上保证:根脚本成功返回时,未等待的 Task.Run、async 函数或 continuation 仍可能在**该执行器进程**里继续运行,但那个进程在本次调用返回前就被杀掉并等待退出,残留随之消失;`RequiresTermination=false` 不再被当作“进程健康”的证明。`active-run` 绑定仍负责拒绝迟到的工具调用。**仍未做**:文件/网络/进程权限沙箱、内存与 CPU 限额、可选的预启动执行器池(只能 Take,不能 Return 已用执行器,须由分段实测决定,不作为当前前提)。

脚本执行器在 POSIX 上现在与插件 Worker 走同一条归属路径:两者都由 Host 的 `posix_spawnp` 启动、都在 spawn 内自成一组的组长,`kill(-pid, SIGKILL)` 因此有组可杀(此前执行器从不 `setpgid`,那一步必然得到 `ESRCH`,只能靠 `Process.Kill(entireProcessTree: true)` 枚举兜底)。这仍不等于 Windows Job Object:**后代可 `setsid`/`setpgid` 逃逸、Host 被强杀时 POSIX 侧没有 KILL_ON_JOB_CLOSE 等价物**(只剩管道断开让进程自行退出,残留后代不被清理);不合作的“整棵进程树”最终仍由枚举式兜底和随后的“进程是否真的消失”验证兜住,兜底在枚举之后新生或已逃脱的后代上会漏。真正的减轻措施没变:执行器被禁止启动子进程(只接受 `--pipe`,不提供进程/文件/网络能力,脚本侧的编译白名单与语义检查也拒绝进程 API),所以“整棵进程树”实际就是一个进程。这些限制是平台限制,不因迁移而消失。

“常驻编译 + 一次性执行器”已切换到正式路径(见 `forge-architecture`)。work78 分段实测:暖调用约 134–137 ms,其中进程创建约 48 ms、新进程首次初始化约 38 ms 为最大项,杀树约 2 ms;本次实现自测同样口径约 129–131 ms(编译 0.1 ms + spawn/connect 47–58 ms + load 53–82 ms + run 24–34 ms)。R2R、Concurrent GC/TieredPGO 与预启动池都仍须对照测量,不作为承诺;未实测的收益不写进验收。
